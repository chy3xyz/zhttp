# HTTP/3 (httpz.h3)

Native HTTP/3 over QUIC. The transport is zquic (Zig, vendored at
vendor/zquic) and framing/QPACK live in src/h3/native/. OpenSSL is used only for
the TLS 1.3 handshake through SSL_set_quic_tls_cbs. ngtcp2 and nghttp3 are no
longer used.

Off by default: build with -Dh3=true.

## Requirements

- Zig 0.17.
- OpenSSL 3.6 or newer, for SSL_set_quic_tls_cbs.
- zquic, vendored at vendor/zquic. Refresh that snapshot from ../zquic when
  the transport changes.

## Architecture

~~~
httpz.h3.Client / httpz.h3.Server     src/h3/Client.zig, src/h3/Server.zig
http3.Session                         src/h3/native/http3.zig
qpack                                 src/h3/native/qpack.zig
transport.Connection / Listener       src/h3/native/transport.zig
crypto_stream.CryptoStream            src/h3/native/crypto_stream.zig
stream_table.StreamTable              src/h3/native/stream_table.zig
flow_control.FlowControl              src/h3/native/flow_control.zig
packet_io.PacketIo                    src/h3/native/packet_io.zig
qtls.Tls                              src/h3/native/qtls.zig
zquic                                 packet protection, PN spaces, loss timers,
                                      stream IDs, frame codec
~~~

One datagram: the listener routes by destination connection ID; coalesced QUIC
packets are split and decrypted by zquic; CRYPTO frames are reassembled per
level and handed to OpenSSL; traffic secrets are expanded into RFC 9001 keys
and installed; STREAM frames go to the HTTP/3 session; the transport tracks
ACK ranges, while zquic detects loss and names the retained plaintext to
resend; the transport then writes queued packets. `packet_io.zig` owns the
socket/datagram seam: bind, recvfrom/poll, destination-CID parsing, coalesced
packet splitting, QUIC varints, random CIDs, and sendto.

### CRYPTO/TLS state

`crypto_stream.CryptoStream` owns the TLS 1.3 context, zquic packet
protection, the four per-level CRYPTO reassemblers, traffic secrets, the
RFC 9001 Initial/Handshake/Application key flags, and the cached Initial flight
that answers a Retry. `transport.Connection` still creates `qtls.Tls` because
it needs the encoded transport parameters, then attaches it; the stream owns
the destroy. Only the newly contiguous CRYPTO prefix is handed to OpenSSL.
`progress()` harvests secrets, installs any newly complete key set, flushes TLS
output in level order, and returns the peer transport parameters and the
TLS-finished flag. Packet scheduling, transport parameters, and the
established/handshake-done bookkeeping stay in Connection, so the split does
not change the wire image, qlog events, or recovery behavior.

## API

~~~zig
const h3 = httpz.h3;

fn handle(allocator: std.mem.Allocator, request: *const h3.Request) h3.Response {
    if (request.method != .GET) return .{ .status = .method_not_allowed, .body = "only GET" };
    return .{ .body = "ok" };
}

try h3.quic.setServerCert(cert_pem, key_pem);
var server = try h3.Server.init(allocator, 4433, handle, .{});
defer server.deinit();
try server.run();
~~~

~~~zig
var client = try h3.Client.init(allocator, "example.com", 443, .{});
defer client.deinit();
const body = try client.get("/");
defer allocator.free(body);
~~~

ClientTls verifies against the system CA store by default. Set
insecure_skip_verify for local self-signed testing only.

## Server options

- idle_timeout_ns, default 30s.
- closing_period_ns, default 3s.
- max_request_body_bytes, default 1 MiB. A larger body is answered with 413.
- initial_max_data / initial_max_stream_data, default 16 MiB. These are the
  receive flow-control windows advertised to clients.
- retry, default true. Tokenless Initials get an HMAC Retry packet before a
  Connection/Session is allocated. The token validates the client address, so
  the server may send handshake bytes without first spending its RFC 9000
  Section 8.1 anti-amplification budget. The built-in client answers Retry, as
  does aioquic. Set `retry = false` only for controlled low-latency tests.
- An unknown method is answered with 501 without calling the handler.

Use `Server.initWithContext(allocator, port, &app, App.handle, .{})` when the
handler needs per-server state; `App.handle` receives the context pointer.

### Router adapter

`h3.Adapter` wraps a normal zhttp `Connection.Handler` — including
`Router.handler(...)` — for the H3 server:

~~~zig
var adapter = try h3.Adapter.create(allocator, io, Router.handler(&routes), .{});
defer adapter.destroy();
var server = try h3.Server.initWithContext(
    allocator, 4433, adapter, h3.Adapter.contextHandler(), .{});
~~~

The adapter copies the response into a per-request arena, lowercases header
names, and supports `stream_fn` by buffering up to `max_buffered_stream`
(default 1 MiB). WebSocket/101 results become 501. `io` must be the Io used by
the thread running the server. Returned slices live until the next request.
See `examples/server_h3_router.zig` for GET/POST routes served over H3.

### Mutual TLS

~~~zig
try h3.quic.setServerCert(cert_pem, key_pem);
try h3.quic.setClientCa(ca_pem); // require a client certificate
~~~

`setClientCa` must run after `setServerCert` and before accepting
connections; it installs the CA and turns on peer verification.

## Streaming responses

Set Response.body_reader and body_context. The server calls the reader from its
event loop while the stream has room, sends the bytes, and sends FIN when the
reader returns 0. No content-length is sent for a streamed body. If the reader
owns resources, set Response.body_reader_deinit; it runs exactly once when the
reader finishes, fails, or the stream is torn down.

## QPACK

SETTINGS advertises `QPACK_MAX_TABLE_CAPACITY = 4096` and
`QPACK_BLOCKED_STREAMS = 16`. Both directions use a dynamic table; the
decoder-side table and blocked-stream resume are unchanged.

The decoder owns a dynamic table bounded by that 4096-byte advertisement. It
applies the peer's encoder stream in order: Set Dynamic Table Capacity (up to
4096), Insert With Name Reference (static or dynamic), Insert With Literal
Name, and Duplicate. Entry size is `name.len + value.len + 32`; a full table
evicts oldest-first, and reducing capacity evicts until the live entries fit.
Field sections resolve pre-base and post-base indexed and name-reference field
lines against entries that have already been inserted, including Required
Insert Count wraparound and positive or negative Delta Base.

The encoder owns a second dynamic table sized by the peer's
`SETTINGS_QPACK_MAX_TABLE_CAPACITY` (capacity zero until those SETTINGS
arrive, which keeps early sections static-only). Once configured, the session
queues exactly one Set Dynamic Table Capacity instruction on its local QPACK
encoder stream (type 0x02), followed by Insert With Literal Name, Insert With
Name Reference, or Duplicate instructions as values are inserted. Encoder
policy:

- Exact static-table matches are indexed field lines. A field whose name is in
  the static table uses a static name reference for literals and inserts.
- A regular field is inserted only when its `name.len + value.len` is at least
  40 bytes, the table capacity is nonzero, the entry size is at most a quarter
  of the table capacity, and the insert would not evict a referenced entry.
- Pseudo-headers, `cookie`, `date`, and `set-cookie` are never inserted.
- Dynamic entries are referenced only when the peer can resolve them. With
  `SETTINGS_QPACK_BLOCKED_STREAMS = 0` an entry must be below the peer's
  acknowledged Insert Count. Otherwise up to `min(peer limit, 16)` streams may
  reference entries the peer has not acknowledged yet; the encoder tracks those
  blocked streams and their per-stream references.
- A section that references dynamic entries carries the RFC 9204 prefix:
  Required Insert Count encoded from the peer's maximum capacity, Delta Base 0,
  and pre-base field-line indexes.
- Outstanding references pin entries. An insert that would evict one is
  replaced by a literal (with a static or dynamic name reference where one
  applies) rather than issuing the insert.

The session also parses the peer's decoder stream (type 0x03) instead of
rejecting it. Section Acknowledgment releases the stream's outstanding dynamic
references, Stream Cancellation drops them without an acknowledgment, and
Insert Count Increment advances `known_received_count`. An increment of zero or
one larger than the outstanding insert count, a malformed instruction, or a
Section Acknowledgment for a stream with no outstanding reference closes with
`QPACK_DECODER_STREAM_ERROR` (0x0203). Encoder-stream violations still map to
`QPACK_ENCODER_STREAM_ERROR` (0x0202).

The session owns the local QPACK decoder unidirectional stream (type 0x03),
opened in `begin()`. After a batch of peer encoder instructions it queues an
Insert Count Increment covering exactly the inserts applied but not yet
acknowledged. After every decoded field section with a nonzero Required Insert
Count it queues a Section Acknowledgment for that request stream. A stream
retired while a Section Acknowledgment is still queued, or while parked on
future inserts, is cancelled with a Stream Cancellation instruction. Writes are
fixed-size and queue directly on the transport stream; when more than 64 KiB is
already pending the session leaves increments and section acks pending and
retries them from `service()`. Staged encoder instructions are flushed from
`service()` and after encoding a section; the flow stays bounded by the
encoder table.

A HEADERS frame whose Required Insert Count is ahead of the peer's encoder
stream is parked, not consumed: `parse_offset` stays at the frame start and the
reassembler keeps every following byte, so request-stream order is never
changed. On each insert-count advance the session retries parked streams. More
than 16 simultaneously blocked request streams, a blocked stream older than
2 seconds, an unsatisfiable Required Insert Count (outside the
insert-count + MaxEntries wraparound window), or an invalid dynamic reference
closes the connection with `QPACK_DECOMPRESSION_FAILED` (0x0201). A capacity
above 4096, an insert larger than the current capacity, a bad index, or a
malformed encoder instruction closes with `QPACK_ENCODER_STREAM_ERROR`
(0x0202).

RFC 9204 gaps: references are tracked per stream, not per field section, so a
peer that sends multiple dynamic sections on one stream (request/response
trailers with a nonzero Required Insert Count) and acknowledges only the oldest
would release too much; this stack sends one dynamic section per stream, so the
case does not arise locally. The Duplicate instruction is implemented and
round-tripped in tests, but the default insert policy references an existing
exact match instead of duplicating it. The encoder does not run its own
blocked-stream timer: entries stay pinned until Section Acknowledgment, Stream
Cancellation, or Session teardown. A peer RESET_STREAM is not surfaced by the
transport, so only the session's own retirement path produces Stream
Cancellation. Push streams remain unimplemented.

## Not implemented

- 0-RTT early data.
- Connection migration and connection-ID rotation.
- qlog P2/P3: HTTP request/response, settings, stream/flow events, recovery
  metrics, and ring buffering. `Server.Options.qlog`/`Client.Options.qlog`
  already provide connection/packet/loss/Retry/error events; the legacy
  `h3.quic.enableQLog` remains a no-op.

## Flow control

`flow_control.FlowControl` owns the per-stream flow map and every connection
and stream window counter. It is plain state: it takes the endpoint
orientation and the peer's transport-parameter limits as values, decides which
`MAX_DATA`/`MAX_STREAM_DATA`/`MAX_STREAMS` frames are due, and never imports
the transport or a `Connection`.

The transport tracks the peer's `initial_max_data` and per-stream limits and
will not put more STREAM bytes on the wire than those windows allow. As data
arrives, the receive side sends `MAX_DATA` once half of the connection window
is consumed and `MAX_STREAM_DATA` on the same threshold per stream. When a
peer-initiated bidirectional stream closes (both FINs seen), the transport
issues `MAX_STREAMS` so the peer can replace it. Opening a stream past the
peer's `initial_max_streams_*` returns `error.StreamLimitExceeded`.

Collection only decides. The advertised receive limit and the last-sent stream
counters advance in the `commit*` methods only after the packet carrying the
control frame was scheduled successfully, so a failed schedule retries the same
window update instead of double-advancing it.

## Stream send table

`stream_table.StreamTable` owns the per-stream send buffers, the STREAM batch
builder, the finished-stream list, and the retired-stream bitset. It never
imports `transport.zig` and knows nothing about `Connection`. Every call takes a
small context: the allocator, the connection's `Stats`, its `FlowControl`, and
the endpoint orientation. `flushStreams` also takes a `Sender` that schedules
exactly one protected 1-RTT packet, plus the packet plaintext budget. A control
batch is passed as an opaque interface, so `ACK`/`MAX_*` collection and commit
remain in `transport.zig`.

The transactional boundary is unchanged: the batch builder claims STREAM frames
and the caller schedules them first. Only after `Sender.schedule` succeeds does
`commitStreamBatch` advance `StreamSend.sent`, `FlowControl.sent_data`, FIN
state, and the finished-stream list. A failed send leaves every stream
byte-identical and retries the same offsets on the next service pass.
`Connection` keeps thin forwarding methods (`queueStreamData`,
`pendingStreamBytes`, `streamSendSnapshot`, `flushStreams`) and zquic stream-ID
allocation. CRYPTO frame dispatch, packet scheduling, ACK/control-frame
collection, recovery, and qlog stay in `transport.zig`. The transport splits
are CryptoStream (TLS/CRYPTO), StreamTable (STREAM batching), FlowControl
(windows), and PacketIo (socket/datagram I/O).

## Packet I/O

`packet_io.zig` owns the UDP/datagram seam: it creates and binds sockets,
wraps sendto/recvfrom/poll, parses the destination CID for routing, splits
coalesced QUIC packets, reads QUIC varints, and generates random CIDs.
`transport.Connection` keeps the authoritative `socket` fd and `Listener`
keeps `socket`/`local_addr` because other modules read those fields directly;
`packet_io.PacketIo` holds the per-connection destination address, tx counter,
and `drop_outgoing_every` test hook. `Connection.flush` still owns qlog FIFO
pairing: it calls `PacketIo.sendDatagram` per drained packet, consumes the
pending entry for every attempt, and advances `packets_sent`/`bytes_sent` only
when the syscall succeeds. The drop hook therefore still suppresses the
datagram and its qlog event without changing packet order or retransmission
behavior. `Listener.dispatch` keeps CID routing and Retry; only the socket,
parse, and syscall helpers moved.

## Production safety limits

Two send-side limits keep the native server safe on the public internet.

### RFC 9000 Section 8.1 anti-amplification

A server `Connection` tracks the UDP bytes it receives and the wire bytes it
successfully sends before the client's address is validated. `flush` refuses
any datagram that would exceed three times the received byte count. A blocked
datagram is not dropped: it and every packet behind it are prepended to zquic's
outgoing queue in their original order, and `flush` stops. The next service
pass retries them after more bytes arrive or validation lifts the cap. qlog
pending entries are consumed only for packets that were actually attempted, so
requeued packets keep their FIFO pairing.

Validation happens when `Listener.dispatch` admits a valid Retry token (the
listener calls `markAddressValidated` before the connection's first datagram)
or when a successfully decrypted Handshake or 1-RTT packet arrives. Initial and
0-RTT packets do not validate; forged or unauthenticated datagrams still count
toward the receive budget, as the RFC requires. Retry is therefore on by
default: the token validates the address before the server commits its
handshake flight.

### Congestion window

`SuperConnection.bytesInFlight()` sums `SentPacket.in_flight` payload bytes
across all three packet-number spaces and
`queuedInFlightBytes()` reports the part still sitting in the outgoing queue.
Before each send, `flush` computes the bytes already on the wire, then asks
zquic's `loss_recovery.canSend` whether the next datagram fits. A blocked
packet is moved back to the front of the outgoing queue with the packets behind
it, preserving order and never duplicating or dropping payload; the next ACK
frees window and `flush` resumes. ACK-only packets and Initial/Handshake
packets bypass the check so handshake progress cannot deadlock; the window
itself starts at zquic's existing initial congestion window. No pacing or token
bucket is implemented yet, so a large cwnd can still be emitted in one service
pass.

## Statistics

`Connection.statsSnapshot()`, `Listener.stats()`, `h3.Server.stats()`, and
`h3.Client.stats()` return a `Stats` value by copy. The counters are plain
`u64` fields updated on the connection's normal dispatch/service thread; there
are no locks, atomics, or allocations. Take a snapshot from that thread, or
after the server's `run` has stopped/joined the thread. A saved snapshot does
not point into the connection and remains valid after deinit.

| Field | Incremented when |
|---|---|
| `packets_sent` | `Connection.flush` successfully hands one protected QUIC packet/datagram to `sendto`. Datagrams dropped by the test loss hook or rejected by `sendto` are not counted. |
| `packets_received` | `Connection.handleDatagram` accepts one UDP datagram. Coalesced QUIC packets in that datagram count as one, matching the one-packet-per-datagram send side. Counted before packet authentication, so a corrupt datagram still counts. |
| `bytes_sent` | Wire bytes of the datagrams counted by `packets_sent`. |
| `bytes_received` | Wire bytes of the datagrams counted by `packets_received`. |
| `retransmits` | A lost plaintext copied from zquic's observer is successfully resent under a new packet number. zquic PTO probes drained by `flush` count as sends, not retransmits; empty ACK-only losses are skipped. |
| `streams_opened` | The transport first creates flow state for a stream, whether opened locally by `createBidiStream`/`createUniStream` or by the peer. HTTP/3 control and QPACK streams are included. |
| `streams_closed` | A stream is reaped after both its send and receive sides reached FIN. A connection closed with open streams leaves `streams_opened > streams_closed`; `Stats.activeStreams()` reports that difference without underflow. |
| `flow_updates` | A batch of `MAX_DATA`/`MAX_STREAM_DATA` frames is scheduled successfully; the batch contributes one per frame. |
| `ack_frames_sent` | An `ACK` frame is scheduled successfully by `sendAcks`. |

`Listener.stats()` sums live connections while skipping the duplicate CID keys a
connection is registered under. `Listener.totalStats()` adds counters retained
from connections already reaped. `h3.Server.stats()` returns that total, so it
still reports a completed connection after reaping; `h3.Client.stats()` returns
its single connection's snapshot. Counters saturate at `u64` max rather than
wrapping or panicking.

Retry packets built directly by `Listener.dispatch` before a Connection exists
are not part of any Connection's `packets_sent`; likewise there is no counter
for datagrams dropped by the kernel before `handleDatagram` sees them.

## Resource lifecycle

`Server.run` reaps closed sessions before closed connections, because
`Session.deinit` clears `conn.handler` while the connection is still alive.
The listener removes all CID-map keys for a reaped connection and frees it.
A completed request stream is retired from the HTTP/3 stream map; the stream
table removes its send history once both FINs have been seen, and
`FlowControl` drops the matching flow entry. A small bitset of retired stream
IDs prevents late retransmitted frames from recreating state.

## Packet batching

`StreamTable.flushStreams` assembles one 1-RTT packet from multiple STREAM
frames, including frames from different streams and several chunks of one
stream. The shared plaintext budget comes from the peer's
`max_udp_payload_size` (clamped 1200–1472) minus header, packet number, AEAD
tag, and frame overhead. When the pending control set fits, its frames are
placed ahead of the first STREAM frame and committed once through the opaque
control-batch interface. A batch is transactional: `StreamSend.sent`,
`FlowControl.sent_data`, FIN state and finished-stream bookkeeping advance only
after the packet was scheduled successfully; a failure leaves every stream
byte-identical for the next pass.

## Retransmission

zquic owns loss detection for Initial, Handshake, and 1-RTT. Each
SuperConnection installs the transport's observer with `context = self`; when
zquic declares a packet lost it invokes the observer before freeing the
retained plaintext. The observer copies `{level, packet number, plaintext}`
into a per-connection queue and returns without sending. Empty payloads
(ACK-only packets) are skipped.

`Connection.service` calls `pollLossRecovery` first, then drains the queue and
resends each payload through `sendProtectedRawPacket` under a fresh packet
number. The level mapping is fixed: Initial stays Initial with the Initial
destination/local CID rules, Handshake stays Handshake, and application data
becomes 1-RTT. At most 64 payloads are resent per service pass and 8192 are
retained; the oldest is evicted on overflow.

A short 200 ms grace window absorbs the case where zquic's 1 ms loss floor
fires just before the peer's ACK is read from the socket. This is pacing, not a
second detector: the loss decision remains zquic's. The synthetic
`drop_outgoing_every` test hook bypasses the grace so loss tests stay prompt.
PTO probes remain enabled in zquic, so a tail loss (no later packet to ACK)
still elicits an ACK and lets loss detection surface the original packet.

ACK generation still belongs to the transport: `ack.zig`, `sendAcks`, and the
coalesced 1-RTT control batch. That is the only remaining split. zquic decides
what was lost; the transport emits ACKs for what arrived. `stats.retransmits`
and `test_retransmit_count` increment only when a queued lost payload is
successfully resent, and zquic PTO probes count as ordinary sends. The old
transport SentPacket history is no longer used by `Connection`; `recovery.zig`
is retained only for its isolated unit tests.

## zquic surfaces used

The transport uses:

- PacketCrypto.processProtectedRawPacket / createProtectedRawPacket for packet
  protection;
- SuperConnection.sendProtectedRawPacket and drainOutgoingRawPackets for
  emission, `queueOutgoingRawPacketsFront` for in-order requeue,
  `bytesInFlight`/`queuedInFlightBytes` for congestion accounting,
  `setLostPacketObserver`/the lost payload callback for recovery ownership,
  `pollLossRecovery` for loss detection and PTO probes, and
  processPlaintextPayloadAtLevel for ACK/flow-control dispatch;
- TransportParameters, Tls13KeySchedule.deriveQuicPacketKeys, and
  EnhancedTlsContext/PacketCrypto init for negotiation and key material.

One local zquic fix is required in `src/core/packet_space.zig`:
`processAck` advances `largest_acked_packet` for every valid ACK range, even
when loss detection already removed that packet from `sent_packets`. Without
it, one premature time-threshold loss freezes `largest_acked` and makes every
later send look lost by packet threshold.

ACK ranges are kept in the transport because decryption happens before zquic
sees a packet. Only ACK and flow-control frames are re-serialized into zquic's
dispatcher; CRYPTO and STREAM are owned by this layer. zquic retains the
plaintext of ack-eliciting protected packets; on loss the observer copies it,
and the transport replays that copy at the same level under a new packet
number.

## Notes from the zoxy dependency tree

- zoxy/deps/zssl is a sans-I/O TLS 1.3 implementation. The QUIC-TLS bridge
  follows its hand-bytes-in / take-bytes-out event shape, but zssl has no QUIC
  transport parameters or QUIC key schedule, so OpenSSL remains the handshake
  provider. zssl is a record-layer TLS stack over libcrypto, not a QUIC-TLS
  backend: importing it would add a second TLS implementation without removing
  libcrypto. All OpenSSL C declarations used by h1/h2 and h3 live in
  src/openssl_c.zig; qtls.zig imports that module instead of repeating externs.
- zoxy/deps/h2 and zhttp's src/h2/huffman.zig share the RFC 7541 Huffman code
  that QPACK reuses.
- zoxy/deps/zio and libxev show the event-loop separation used here: the
  transport owns no callbacks into user code, and the server loop only polls,
  dispatches, and services.
